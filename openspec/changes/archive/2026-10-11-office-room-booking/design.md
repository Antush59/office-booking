# Дизайн

## Контекст

Greenfield-проект: репозиторий пуст (нет кода), задан только технический стек — Java 17, Maven, Spring Boot 2.7, PostgreSQL в Docker, Liquibase, TestNG, LogBack, синхронный REST. Ограничения: без UI, без авторизации, без ролевой модели. Данные сохраняются между запусками (решение из обсуждения, см. proposal.md — Зачем).

## Цели / Не-цели

**Цели:**
- Простое и корректное доменное ядро «комната + бронь» с проверкой пересечений.
- Чистый REST-контур с явной валидацией и понятными кодами ошибок (400 / 409 / 404).
- Схема БД, управляемая Liquibase, воспроизводимая на пустой БД.

**Не-цели:**
- Авторизация, аутентификация, ролевая модель.
- UI любого вида.
- Многодневные брони (бронь всегда в пределах одного дня — см. рабочие часы).
- Уведомления, календарная синхронизация, интеграции.

## Решения

### 1. Хранение — Spring Data JPA + Hibernate поверх PostgreSQL
Данные реально сохраняются в БД (требование «данные переживают перезапуск»).
- Альтернатива: in-memory репозиторий — отвергнуто, противоречит решению сохранять данные.
- Альтернатива: чистый JDBC / JdbcTemplate — больше шаблонного кода без выгоды для учебного проекта.

### 2. Модель времени — интервал `start_at` / `end_at` (TIMESTAMP), полуоткрытый `[start, end)`
Бронь занимает промежуток; соседние брони стыкуются без пересечения (`10:00–10:15` и `10:15–10:30` не конфликтуют).
- Альтернатива: таблица фиксированных слотов — лишняя сущность, жёстче для пользователя; отвергнуто.
- Альтернатива: отдельные колонки `date` + `time` — TIMESTAMP проще и покрывает «дату и время» без разбиения; отвергнуто.

### 3. Рабочий день и шаг — 08:00–19:00, минимум 15 минут
Свободные слоты считаются по 15-минутной сетке в пределах рабочего дня; брони обязаны ложиться на границы `:00/:15/:30/:45` и умещаться в день. Значения задаются как константы в конфигурации приложения.

### 4. Отмена — soft-delete через статус `ACTIVE` / `CANCELLED`
Бронь не удаляется физически, а переводится в `CANCELLED`; все проверки занятости учитывают только `ACTIVE`.
- Альтернатива: физическое удаление — проще, но теряет историю «кто бронировал, но отменил»; отвергнуто.

### 5. Проверка пересечений — в сервисном слое внутри транзакции
Перед созданием брони ищутся ACTIVE-брони той же комнаты с пересечением `start1 < end2 AND start2 < end1`. При конфликте — HTTP 409 с именем пользователя и интервалом конфликтующей брони.
- Замечание: обычный уникальный индекс в PostgreSQL не может выразить «непересечение интервалов». Для учебного проекта достаточно транзакционной проверки; см. Риски.

### 6. Схема — Liquibase
Changelog создаёт таблицы `rooms` (id, name, capacity) и `bookings` (id, room_id FK, user_name, start_at, end_at, status), плюс индекс на `(room_id, start_at)` для поиска пересечений.

### 7. REST-контур
```
GET    /rooms                        -> все комнаты + характеристики
GET    /rooms/{id}/free-slots?date=  -> свободные 15-мин слоты на дату
GET    /rooms/free?date=&start=&end= -> свободные комнаты на интервал
POST   /bookings                     -> создать бронь; 400 на валидации, 409 на конфликте
DELETE /bookings/{id}                -> отменить бронь (status = CANCELLED)
```

### 8. Тестирование — TestNG
Юнит-тесты сервисного слоя (логика пересечений, валидация, подсчёт слотов) и интеграционные тесты репозиториев/API поверх PostgreSQL (Docker / Testcontainers).

## Риски / Компромиссы

- [Гонка при параллельном создании пересекающихся броней] → Проверка выполняется в транзакции; при необходимости можно добавить пессимистичную блокировку строки комнаты (`SELECT ... FOR UPDATE`) или exclusion constraint через `btree_gist` (расширение Postgres). Для учебного проекта достаточно транзакционной проверки.
- [Часовые пояса и границы дня] → Хранить `start_at`/`end_at` в UTC, рабочее время интерпретировать в локальной зоне сервера; валидация «в пределах одного дня» опирается на дату `start_at`.
- [Рост таблицы из-за CANCELLED-брони] → Для учебного приложения несущественно.
